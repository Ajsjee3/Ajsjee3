# 첫 2주: 주문 한 건이 움직이는 과정 이해하기

목표는 코드를 외우는 것이 아니라, 입력을 바꿨을 때 결과가 어떻게 달라지는지 설명하는 것입니다. 주 6~10시간 안에서 순서대로 진행합니다.

## 1주차

1. README의 실행 명령으로 자동 검증을 실행합니다. 산출물에서 정상 300개, 중복 5개, 오류 4개가 어느 항목에 기록되는지 찾습니다.
2. scripts/generate_demo.py에서 주문 한 건의 필드를 읽습니다. source, order_id, revision을 종이에 자신의 말로 정리합니다.
3. orderlens/main.py의 health 함수만 읽습니다. 브라우저의 URL과 함수 이름이 달라도 연결되는 이유를 확인합니다.
4. schemas.py에서 금액 검증을 확인합니다. 1000, -1000, 10.5, "1000"을 각각 보냈을 때 어떤 값이 허용되는지 실행 전에 예상합니다.
5. 새로운 Python 파일에서 FastAPI의 /hello API를 직접 만들고 문자열 한 개를 반환합니다. 기존 코드를 참고해도 괜찮지만 설명할 수 있는 분량으로 작성합니다.

완료 기준: "요청 → 입력 검증 → 함수 → 응답"을 코드와 연결해서 3분 정도 설명할 수 있습니다.

## 2주차

1. 같은 주문을 두 번 보내고 새로 저장된 버전 수와 중복 수를 비교합니다.
2. 같은 revision에서 금액만 바꾸면 왜 충돌이 되는지 확인합니다. revision을 올렸을 때와 비교합니다.
3. orderlens/models.py의 세 테이블이 각각 무슨 일을 하는지 적습니다.
4. 테스트의 작은 주문 5건을 손으로 계산합니다. 취소·환불 금액을 합계에서 제외한 결과가 600원이 되는지 확인합니다.
5. 추가된 /v1/orders/attention의 source 필터를 읽습니다. limit=1로 요청했을 때 경로 필터가 먼저 적용되는 이유를 작은 입력으로 확인하고 자신의 말로 기록합니다.

완료 기준: "입력 행 수, 저장한 버전 수, 최신 주문 수는 왜 다를까?"를 예제로 설명할 수 있습니다.

## 막혔을 때 남길 기록

실행 명령, 실제 오류 문구, 예상했던 결과, 바꾼 입력을 같이 기록합니다. 전체 코드를 다시 생성하는 대신 한 번에 오류 한 개를 좁혀 갑니다.

도움을 요청할 때는 예를 들어 "schemas.py의 StrictInt가 왜 필요한지 -1000과 10.5를 기준으로 설명해 주세요"처럼 파일과 상황을 함께 주시면 됩니다.
