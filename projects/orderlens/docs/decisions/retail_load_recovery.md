# 공개 거래 적재 시도와 복구 기록

작성: 2026-10-19 · 버전: 0.7.0

## 문제

기존 적재는 한 트랜잭션으로 동작해 잘못된 후반부 행이 있으면 앞서 넣은 행도 모두 되돌렸습니다. 데이터 정합성은 지켰지만, 롤백 뒤에는 실패한 실행 자체도 DB에 남지 않았습니다. 운영자가 어떤 원본을 언제 시도했고 왜 실패했는지, 다시 실행한 결과가 새 적재인지 이미 처리한 파일인지 구분하기 어려웠습니다.

## 선택한 구조

`retail_load_attempts`의 한 행은 CLI 적재 한 번을 뜻합니다. UUID, 원본 SHA-256, 보고서 SHA-256, 시작·종료 시각과 다음 상태를 보존합니다.

| 상태 | 결과·오류 |
|---|---|
| `running` | 종료 시각·결과·오류가 아직 없음 |
| `succeeded` | 결과가 `loaded` 또는 `already_loaded`, 적재·중복 행 수 기록 |
| `failed` | 제한된 오류 코드와 최대 500자의 안전한 설명 기록 |

CHECK 제약으로 상태와 종료 필드 조합, 음수가 아닌 행 수를 확인합니다. `(source_sha256, started_at)` 인덱스로 같은 원본의 시도를 시간순으로 찾을 수 있습니다. 실패한 원본은 `retail_imports`에 존재하지 않을 수 있으므로 원본 해시에 외래 키를 두지 않았습니다.

## 트랜잭션 경계

1. `report.json`에서 유효한 원본 SHA를 읽고 `running` 시도를 먼저 커밋합니다.
2. 파일 해시·거절 행·정제 행을 검사하고, 실제 import와 거래 행은 별도 트랜잭션에 넣습니다.
3. 데이터 계약이나 DB 작업이 실패하면 실제 적재는 롤백하고 시도를 `failed`로 끝냅니다.
4. 성공하면 시도를 `succeeded`로 끝내고 `loaded` 또는 `already_loaded` 결과를 남깁니다.

계약 오류는 행 위치와 필드 규칙만 저장합니다. DB 예외의 SQL·파라미터와 예상하지 못한 예외 본문은 기록하지 않아 원본 값이나 연결 정보가 오류 문자열로 유출되지 않게 했습니다. CLI 실패 응답은 표준 오류에 `attempt_id`, 상태, 오류 코드와 같은 제한된 설명을 JSON으로 출력해 DB 이력과 연결합니다.

## 재현 결과와 한계

합성 정제 행 두 개를 `batch_size=1`로 읽으며 두 번째 행의 금액 계약을 깨뜨렸습니다. 실패 뒤 `retail_imports=0`, `retail_lines=0`이고 시도 한 건만 `failed/data_contract`로 남았습니다. 파일을 복구한 다음 실행은 2행을 넣었고, 한 번 더 실행하면 새 행 0개·중복 2개였습니다. 세 시도는 `failed → succeeded/loaded → succeeded/already_loaded`로 구분됩니다. 재현 결과는 [retail_recovery.json](../../artifacts/retail_recovery.json)에 있습니다.

`report.json` 자체가 없거나 원본 SHA가 잘못되면 신뢰할 식별자가 없어 DB 시도를 만들지 않습니다. 프로세스가 시도 생성 직후 강제 종료되거나 성공 결과를 갱신하기 전에 종료되면 `running`이 남을 수 있습니다. 오래된 실행을 판정하는 heartbeat·timeout, 동시에 같은 파일을 처음 넣는 경합, 자동 재시도 스케줄러는 아직 구현하거나 검증하지 않았습니다.

직접 확인할 작은 과제: 실패 시도 행과 `retail_imports` 행을 같은 트랜잭션에 넣으면 왜 실패 기록까지 사라지는지, 두 트랜잭션의 순서를 손으로 그려 설명해 보세요.
