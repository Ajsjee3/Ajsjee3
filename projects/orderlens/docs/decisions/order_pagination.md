# 상태별 주문 목록과 페이지 조회

작성: 2026-09-14 · 버전: 0.2.0 · [이슈 #1](https://github.com/Ajsjee3/Ajsjee3/issues/1)

## 필요한 동작

특정 판매 경로에서 아직 결제 상태인 주문을 나눠 조회합니다. 주문이 이미 취소됐다면 이전 결제 버전이 목록에 남아서는 안 됩니다. 주문 시각이 같은 항목도 같은 순서로 반환해야 합니다.

```text
GET /v1/orders?source=market_a&status=paid&limit=2&offset=0&as_of=2026-09-08T00:00:00Z
```

## 조회 순서

1. 원천 갱신 시각 `updated_at <= as_of`인 버전만 남깁니다.
2. `source + order_id`별 가장 큰 `revision`을 선택합니다.
3. 선택한 최신 주문에 `source`, `status` 필터를 적용합니다.
4. `placed_at DESC, source ASC, order_id ASC`로 정렬합니다.
5. SQL에서 `OFFSET offset LIMIT limit + 1`을 적용합니다.

정렬의 마지막 두 필드는 최신 주문의 고유 키입니다. 같은 주문 시각이라도 순서가 정해집니다. 상태 필터를 2번보다 먼저 적용하면 취소된 주문에서 과거의 `paid` 버전이 다시 선택되므로 순서를 바꾸면 안 됩니다.

## 응답과 선택 이유

| 항목 | 계약 |
|---|---|
| orders | 입력과 같은 공개 주문 필드, 주문별 최신 버전 최대 limit건 |
| as_of | 실제 사용한 기준 시각을 UTC로 반환; 생략하면 첫 요청의 현재 시각 |
| source, status | 요청한 필터; 생략하면 null이며 전체 대상 |
| limit | 기본 20, 1~100 |
| offset | 기본 0, 0~9,223,372,036,854,775,807; DB 정수 범위를 넘으면 422 |
| has_more | 조회 결과가 limit보다 많으면 true |
| next_offset | 다음 데이터가 있으면 offset + limit, 없으면 null |

`limit + 1`건을 읽어 다음 페이지 존재 여부를 확인하고 마지막 한 건은 응답에서 제외합니다. 전체 건수나 전체 페이지 수가 필요한 요구사항은 없어 별도 COUNT 쿼리는 넣지 않았습니다. 내부 DB ID, 내용 해시, 버전 순위는 응답에서 제외합니다.

이번 범위에는 별도 커서 형식 없이 요청과 SQL의 관계를 확인할 수 있는 offset 방식을 선택했습니다. 임의 위치를 요청하기는 쉽지만 큰 offset에서 빠르다는 뜻은 아닙니다. SQL 성능은 아직 측정하지 않았습니다.

잘못된 경로·상태·범위나 시간대 없는 `as_of`는 422입니다. 결과가 없거나 마지막 위치를 넘으면 200과 빈 목록을 반환합니다. 공통 API 키가 없으면 401입니다. 경로 필터는 사용자별 접근 권한 기능이 아닙니다.

## 페이지 사이에 데이터가 바뀌면

데이터가 바뀌지 않고 `as_of`, 필터와 정렬 조건을 유지하면 주문마다 한 번씩 조회됩니다. 다음 요청에는 응답의 `as_of`와 `next_offset`을 재사용합니다.

`as_of`는 원본의 갱신 시각 조건이지 DB 스냅샷이 아닙니다. 기준 시각 이후에 갱신된 새 버전은 제외되지만, 과거 갱신 시각을 가진 주문이나 높은 버전이 뒤늦게 들어오면 결과가 바뀔 수 있습니다. 새 주문이 앞에 끼어들면 다음 페이지에 이전 주문이 다시 나오고, 주문이 필터에서 빠지면 아직 읽지 않은 주문을 건너뛸 수 있습니다.

테스트에서는 같은 시각의 B·C 주문 중 B를 읽은 뒤 A를 추가하면, `offset=1`에서 B가 다시 나오는 사례를 재현합니다. 이 동작을 무중복 보장으로 설명하지 않습니다. 여러 요청에 걸친 일관성이 필요해지면 적재 시각 기준 또는 스냅샷 정책을 먼저 정해야 하며, 커서만 도입한다고 모든 상태 변경 문제가 해결되지는 않습니다.

## 검증과 참고

[test_order_pages.py](../../tests/test_order_pages.py)에서 페이지 크기 1·2·3·4·100, 동률 정렬, 경로 간 같은 주문 번호, 다섯 상태, 취소 버전, 첫·마지막·빈 페이지, 잘못된 입력, 기준 시각과 뒤늦은 적재를 확인합니다.

```bash
python -m pytest -q tests/test_order_pages.py
python -m scripts.check
```

전체 검증의 실제 HTTP 단계에서는 적재된 120건을 17건씩 8페이지로 조회하고, 고유 주문 수도 120인지 비교합니다. 테스트 결과와 환경은 [검증 기록](../validation.md), 참고한 외부 소스와 적용 범위는 [참고 기록](../references.md)에 남깁니다.

직접 확인할 작은 과제: `limit=2`로 첫 페이지와 다음 페이지를 조회한 뒤, `next_offset`이 어떤 위치를 가리키는지 자신의 말로 설명해 보세요.
