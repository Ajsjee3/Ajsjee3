# PostgreSQL 통합과 스키마 마이그레이션

작성: 2026-09-21 · 버전: 0.3.0

## 해결하려는 문제

기존 앱은 시작할 때 SQLAlchemy의 `create_all`로 없는 테이블을 만들었습니다. 새 DB를 빠르게 시작하기에는 편하지만, 어떤 스키마 변경을 언제 적용했는지 남지 않습니다. 코드만 이전 버전으로 되돌려도 DB 구조는 자동으로 돌아가지 않으며, 마이그레이션이 빠진 배포도 앱 시작 과정에서 가려질 수 있습니다.

이번 변경부터 Alembic 리비전을 스키마의 기준으로 사용합니다. 첫 리비전 `20260921_01`은 다음 세 테이블과 주문 버전의 UNIQUE 제약, 갱신 시각 인덱스를 명시합니다.

- `ingestion_runs`: 한 번의 적재 결과
- `order_snapshots`: 주문별 버전 이력
- `rejected_rows`: 검증 실패 위치와 유형

## 실행 순서

```text
빈 DB → alembic upgrade head → API 시작 → 현재 리비전 확인 → 요청 처리
```

앱은 시작할 때 DB의 현재 리비전과 코드의 head를 비교합니다. 다르면 테이블을 임의로 만들지 않고 `python -m alembic upgrade head`가 필요하다는 오류로 중단합니다. 마이그레이션 실행 권한과 일반 API 권한을 나눌 수 있게, 앱 프로세스가 스키마를 바꾸지 않도록 했습니다.

Docker Compose에서는 `db`가 준비된 뒤 일회성 `migrate` 서비스가 upgrade를 실행합니다. 성공한 경우에만 `api`가 시작합니다. 일반 Python 실행에서는 사용자가 서버 시작 전에 같은 명령을 한 번 실행합니다.

## 검증 방법

기본 검증의 `scripts.check_migrations`는 임시 SQLite DB에서 다음 순서를 확인합니다.

1. head까지 올린 뒤 세 업무 테이블, UNIQUE 제약과 인덱스를 확인하고 모델과 리비전 사이의 차이가 없는지 검사합니다.
2. base로 내린 뒤 업무 테이블과 현재 리비전이 남지 않았는지 확인합니다.
3. 다시 head까지 올리고 앱이 현재 스키마로 판단하는지 확인합니다.
4. 마이그레이션하지 않은 DB에서는 앱이 시작을 거부하는지 테스트합니다.

PostgreSQL 검증은 이름이 `_test`로 끝나는 전용 DB만 허용합니다. GitHub Actions의 임시 PostgreSQL 16 서비스에서 마이그레이션을 적용한 뒤 합성 데이터 309행을 적재·재전송하고, 지표와 8페이지 주문 목록을 비교합니다. 마지막에는 downgrade와 재upgrade도 실행합니다. [실제 원격 실행](https://github.com/Ajsjee3/Ajsjee3/actions/runs/35590864397)은 PostgreSQL 16.15에서 통과했으며 상세 값은 [검증 기록](../validation.md)에 남겼습니다.

## 선택과 남은 범위

첫 리비전은 현재 SQLAlchemy 모델을 그대로 옮긴 기준점입니다. 실제 운영 데이터가 이미 있는 DB를 이 리비전으로 전환하는 절차는 이번 범위가 아닙니다. 새 컬럼을 추가하는 두 번째 리비전과 데이터 보정, 여러 앱 인스턴스의 배포 순서도 이후 변경에서 별도로 검증해야 합니다.

테스트용 스크립트는 테이블을 내리므로 일반 `ORDERLENS_DATABASE_URL` 대신 `ORDERLENS_POSTGRES_TEST_URL`만 읽고 DB 이름의 `_test` 접미사를 검사합니다. 이 문자열 검사는 마지막 안전장치일 뿐이며, 실제 환경에서는 별도 계정·DB와 최소 권한도 함께 사용해야 합니다.

직접 확인할 작은 과제: 새 빈 DB에서 `alembic current`, `alembic upgrade head`, `alembic current`를 차례로 실행하고 `없음 → 20260921_01`로 바뀌는 이유를 설명해 보세요.
