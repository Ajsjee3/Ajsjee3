# 설계와 지표 정의

## 해결하려는 문제

판매 경로마다 들어오는 주문 파일이 중복되거나 잘못된 값을 포함하면 주문 금액과 지연 건수가 틀릴 수 있습니다. 주문 상태가 여러 번 변경되므로 입력 행 수를 주문 수로 세어서도 안 됩니다. 이 프로젝트는 검증과 집계 과정을 재현하고, 지표의 근거를 확인할 수 있는 작은 운영 API입니다.

초기 사용자는 한 판매점의 운영 담당자로 가정했습니다. 여러 고객사의 데이터가 분리되는 SaaS 권한 구조는 후속 범위입니다. 모든 동작 예제와 업무 문서는 직접 만든 가상의 규칙입니다.

## 데이터 계약

| 필드 | 규칙 |
|---|---|
| source | market_a, market_b, own_store 중 하나 |
| order_id | 판매 경로 내 주문 식별자; 영문·숫자·밑줄·하이픈 |
| revision | 1 이상의 정수; 상태를 바꾸면 증가 |
| placed_at | 주문 시각; 시간대 필수 |
| updated_at | 해당 버전의 원천 갱신 시각; 주문 시각 이후 |
| promised_by | 배송 예정 시각; 주문 시각 이후 |
| delivered_at | 실제 배송 시각; 배송 완료 상태이면 필수 |
| status | paid, shipped, delivered, cancelled, refunded |
| amount_krw | 0 이상의 정수 원화; 문자열·소수·불리언 제외 |

현재 버전은 부분 환불, 결제 재시도, 복수 상품, 수수료, 세금, 환율을 계산하지 않습니다. 따라서 금액 지표를 회계상 매출·이익으로 해석하지 않습니다.

## 왜 버전 이력을 보관할까요?

`source + order_id + revision`에 DB UNIQUE 제약이 있습니다. 같은 키와 같은 내용은 중복, 같은 키와 다른 내용은 충돌입니다. 내용 비교 전에는 시간대를 UTC로 정규화합니다. 따라서 같은 순간을 Z와 +09:00으로 다르게 표현해도 중복으로 인식합니다.

높은 버전이 먼저 도착하고 낮은 버전이 나중에 도착해도 이력은 각각 저장합니다. 조회할 때 SQL의 ROW_NUMBER로 주문별 가장 큰 revision을 선택합니다. 모든 버전을 그대로 더하면 주문 수와 금액이 부풀기 때문입니다.

revision이 높을수록 최신이라는 원천 데이터 계약에 의존합니다. 현재 구현은 서로 다른 버전 사이의 updated_at 단조 증가와 상태 전이 규칙을 강제하지 않습니다. 그 규칙은 실제 데이터 제공자의 계약을 확인한 다음 추가해야 합니다.

## 시간 조회의 의미

as_of 시각보다 늦게 갱신된 버전을 제외한 뒤, 남은 버전 중 가장 큰 revision을 고릅니다. 이 조회는 **원천 갱신 시각 기준 조회**입니다. 늦게 도착한 과거 자료를 나중에 적재하면 과거 as_of 조회 결과도 달라질 수 있습니다. 당시 시스템이 알고 있던 정보까지 정확하게 복원하려면 별도 ingested_at 조건과 이중 시간 모델이 필요합니다.

start_at과 end_at은 선택된 주문의 placed_at에 적용됩니다. start_at은 포함, end_at은 제외합니다. 입력의 +09:00과 Z는 같은 UTC 기준으로 비교합니다.

## 주문 목록 조회

`GET /v1/orders`는 최신 버전을 고른 뒤 판매 경로·상태를 거릅니다. 정렬은 `placed_at DESC, source ASC, order_id ASC`이며 SQL의 LIMIT·OFFSET으로 목록을 나눕니다. 한 건을 더 조회해 다음 페이지 존재 여부를 판단하고 전체 COUNT는 계산하지 않습니다.

다음 요청은 응답의 `as_of`와 필터를 유지해야 합니다. 다만 원천 갱신 시각 조건은 적재 데이터 자체를 고정하지 않으므로, 뒤늦은 과거 자료가 들어오면 페이지 경계가 달라질 수 있습니다. [페이지 조회 결정 기록](decisions/order_pagination.md)에 API 계약, 선택 이유와 재현 사례를 정리했습니다.

## 지표 정의

| 지표 | 계산 |
|---|---|
| total_orders | 조회 조건을 만족하는 최신 주문 수 |
| active_orders | paid 또는 shipped 주문 수 |
| delivered_orders | delivered 주문 수 |
| cancelled_orders | cancelled 주문 수 |
| refunded_orders | refunded 주문 수 |
| overdue_open_orders | 미완료 상태이면서 promised_by < as_of인 주문 수 |
| late_delivered_orders | delivered 상태이면서 delivered_at > promised_by인 주문 수 |
| booked_amount_krw | paid, shipped, delivered 상태의 금액 합 |
| late_delivery_rate | late_delivered_orders / delivered_orders; 분모 0이면 null |

배송 예정 시각과 실제 배송 시각이 같으면 지연으로 세지 않습니다. 취소·환불 주문은 유효 주문 금액에서 제외합니다. 환불된 주문은 배송 지연율 분모에서도 제외하므로, 환불 전후에 이 비율이 달라질 수 있습니다. 주문 코호트의 역사적 배송 품질을 분석하려면 별도 지표를 정의해야 합니다.

## 실패와 재시도

개별 데이터 검증 실패는 정상 행의 적재를 막지 않습니다. 행 번호와 필드 오류 유형을 기록합니다. 예측하지 못한 처리 실패는 전체 배치 트랜잭션을 되돌립니다. 한 행의 UNIQUE 충돌은 SAVEPOINT로 다룹니다.

재전송해도 주문 버전이 중복 생성되지 않습니다. 다만 매 API 호출마다 처리 이력은 새로 남습니다. quality API의 오류 수는 **재시도를 포함한 입력 시도 수**이며 고유한 오류 주문 수가 아닙니다. 실패 원문을 따로 보관하지 않으므로, 수정 재제출에는 사용자가 가진 원본 JSON이 필요합니다.

SQLite는 쓰기 동시성에 제약이 있고 운영 오류에는 HTTP 503을 반환합니다. 병렬 부하에서 모두 성공한다는 보장은 검증하지 않았습니다. 운영 전에는 PostgreSQL에서 동시 중복 요청, 잠금, 재시도 정책을 검증해야 합니다.

## 검색과 AI 확장

한국어 2글자 조각과 영문 토큰으로 BM25 점수를 계산합니다. 문서 ID와 버전을 함께 반환하며 점수를 확률로 표현하지 않습니다. 검색어와 겹치는 글자가 있다고 해서 관련성이 보장되지는 않습니다.

현재 brief는 지표를 고정 문장에 넣고 관련 문서를 첨부하는 규칙 기반 결과입니다. LLM을 호출하지 않습니다. 다음 단계에서는 문서와 질문을 분리한 평가 집합, 임베딩 검색, 근거를 인용하는 답변, 근거가 부족할 때 답변 보류, 호출 비용·응답시간 측정을 구현합니다.

## 운영 확장 전에 남은 일

DB 마이그레이션, 사용자별 권한과 데이터 분리, 비밀 키 관리, 요청 본문 크기 제한, 외부 공개용 HTTPS, 요청 제한, 백업 복구, 동시성·장애 복구 시험, 실제 데이터 평가가 남아 있습니다. 현재 create_all은 새 스키마 생성용이며 기존 테이블 구조를 자동 변경하지 않습니다.
